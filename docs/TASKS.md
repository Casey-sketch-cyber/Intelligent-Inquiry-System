# 任务卡（2026-11-19 审查后拆分）

来源：Claude 对 `main@8bcb3f5` 的代码审查。目标是提高速度、稳定性和易用性，减少触发 IC交易网验证码和 QQ 风控的机会，并把大模型逐步接入“判断”环节。

## 使用方法

- 每次只领一个任务。开工前确认依赖已合并，状态改为“进行中”。分支名用 `<工具名>/T<编号>-<简述>`，例如 `codex/T01-search-throttle`。
- 每个任务一个 PR。PR 说明逐条对照下面的“验收”，写明满足、未满足或只能实机验证。
- 标有 **【需实机】** 的验收项不能用离线测试代替。在 PR 中写明“未实机验证”。实际发送 QQ 消息必须先得到用户授权（见 `AGENTS.md`）。
- 审查者合并后把状态改为“完成”，退回时改为“退回”。

## 红线（所有任务都适用）

以下做法一律不做，也不要以“可选开关”的形式加入：

- 自动识别或自动填写验证码，包括调用大模型或视觉模型看图、接入打码平台，或模拟拖动滑块。验证码只能由人处理。
- 代理池、轮换 IP、伪造浏览器指纹、多个 QQ 号轮流发送。
- 为了躲避重复内容检测而随机改写询价话术。
- 调高发送上限，即最短间隔 20 秒、每小时 60 次（`dispatch.rate_delay` 的硬上限保持不变）。
- 由大模型直接根据截图操作界面（点击、输入）。界面操作只由确定性的脚本执行，大模型只在白名单动作中做选择。

## 一、搜索与速度

### T01 全局持久化搜索限速

**问题**：只有 `runner.load_candidates()` 带 30 秒间隔。`runner.open_chat()` 经 `icnet.find_row()` 调用 `icnet.search()` 时没有任何限速，找不到供应商会连续翻最多 3 页。这很可能是验证码的主要来源。

**做法**：
- 新增 `search_attempt` 表（`created_at`、`part_no`、`page_no`、`source`），结构参照 `send_attempt`。所有对 IC交易网搜索页的 `page.goto` 都通过 `icnet.search()` 内部的同一个闸门：先等待，再记录，再请求。
- 在 `settings.example.toml` 的 `[pacing]` 中新增 `search_min_interval`（默认 30 秒）和 `search_max_per_10min`（默认 10 次）。闸门在 `inquiry/` 内实现，可参考 `dispatch.rate_delay`。重启后额度不清空。
- 等待期间响应停止请求，不阻塞 UI 线程。
- 删除 `load_candidates()` 中原有的 30 秒逻辑，避免两套限速并存。

**验收**：
- [ ] 新增离线测试：连续调用 `icnet.search()`（`page` 用替身），实际请求间隔不小于 `search_min_interval`，10 分钟内的次数不超过上限。
- [ ] `find_row()` 翻页时同样受限速约束（测试覆盖）。
- [ ] 重启后读取 `search_attempt`，限速依然生效（测试覆盖）。
- [ ] 全部离线回归通过。

### T02 按型号顺序发送、即时搜索

**问题**：
1. `runner.run()` 会先对所有型号执行 `load_candidates`，搜完才发第一条。100 个型号要先搜约 50 分钟。
2. `runner.loop()` 用 `send_wave(quota=1)` 在型号间轮流发送。`icnet.search_page()` 最多保留 20 个搜索标签页，超出后复用第 1 个，所以型号超过 20 个时几乎每次发送前都要重新搜索。

**做法**：
- 常规批次（`send_only`）改为：型号 A 搜索 → A 的各家依次发送 → 型号 B 搜索 → ……。下一个型号的搜索放在发送间隔的等待时间里进行，前提是满足 T01 的限速。
- 同一时间只保留当前型号和下一个型号的搜索标签页，用完即关。删除“超过 20 个就复用第一个”的逻辑。
- 发送限速（`wait_rate_limit`、`dispatch.rate_delay`）和停止语义保持不变。

**验收**：
- [ ] 离线测试：3 个型号、每个 3 家的批次，用 `icnet` 替身统计 `search` 调用次数。无翻页时每个型号恰好 1 次，不出现 `find_row` 引起的重新搜索。
- [ ] 离线测试：第一条发送发生在第一个型号搜索完成后，不再等全部型号搜完。
- [ ] 30 个型号的模拟批次中，打开的搜索标签页不超过 2 个。
- [ ] `tests/test_normal_flow.py`、`tests/test_launch_errors.py` 等现有测试通过。
- [ ] 【需实机】用试运行模式跑 5 个型号，记录搜索次数和总耗时，写进 PR。

### T03 保存供应商 QQ 唤起链接，减少重复搜索

**问题**：`extract_rows.js` 只从 `inthref` 中截取了 uin。发送前要靠 `find_row` 重新定位页面上的行，网页排序一变就要重新搜索。

**做法**：
- `extract_rows.js` 额外保存 QQ 图标的完整 `inthref`（以及 `href`，如果有），并记录到 `supplier` 表的新列。
- 新增开关 `[inquiry] direct_launch = false`。开启后，如果当前页找不到该行，就在专用 Edge 中直接打开保存的链接唤起 QQ，后续仍由 `qq.wait_chat_change`、`verify_supplier` 等原有逻辑核对身份；失败时退回到 `find_row`。
- 先用只读方式实测链接能否唤起临时会话、是否有时效，结论写入 `docs/DECISIONS.md`。如果链接带一次性签名或必须在页面内点击，就不要开启这条路径，只保留链接字段。

**验收**：
- [x] 提取脚本的单元测试覆盖新字段，旧数据缺少该字段时不报错。
- [x] `direct_launch` 默认关闭；关闭时行为与现在完全一致。
- [x] 开启时，身份核对失败仍然阻止发送（测试覆盖）。
- [ ] 【需实机】链接可用性的结论和证据（不含聊天内容）写进 PR 与 `DECISIONS.md`。

### T04 搜索结果缓存

**做法**：用 `search_cache` 按完整型号和页码保存提取后的行和时间。`[filter] search_cache_hours`（默认 4）内试运行可复用缓存。正式询价直接读取实时结果页，只有配置范围内每一页都有有效缓存且当前均无可询价供应商时才跳过搜索。发送时保留原有供应商身份核对。「刷新搜索」可以跳过缓存。

**验收**：
- [x] 离线测试：缓存有效期内第二次读取同一型号的候选供应商不调用 `page.goto`，过期后重新导航。
- [x] 不同后缀、斜杠或连字符的型号不共用缓存。
- [x] 型号详情可查看每次询价使用的缓存页数和缓存取得时间。
- [x] 离线模拟旧缓存中的供应商发生变化时，正式询价使用实时结果，搜索次数与关闭缓存时一致。缺页或过期时仍搜索。

## 三、稳定性

### T06 SQLite 启用 WAL

**做法**：`db.connect()` 中执行 `PRAGMA journal_mode=WAL` 和 `PRAGMA busy_timeout=30000`。检查备份、历史重置和迁移包脚本（`lanhost/reset_history.py`、`lanhost/package.py`、`vmhost/package.py`），确保它们同时处理 `-wal` 和 `-shm` 文件，或继续使用 SQLite backup API。

**验收**：
- [ ] 测试：解析线程、收集线程和 API 写入同时运行时不再出现 `database is locked`（多线程压测，各 200 次写入）。
- [ ] 历史重置和迁移相关测试全部通过，迁移包内的数据库完整可读。

### T07 启动自检：QQ 控件与版本、Edge 版本

**做法**：新增 `inquiry/selfcheck.py`。工作机启动时、每批次开始前，检查 QQ 主窗口中所需控件（`recent-contact-list`、`send-msg`、`chat-msg-area__vlist`、输入框等）能否找到，并读取 QQ 和 Edge 版本。检查不通过时禁止发送，在工作台显示缺少哪个控件以及当前版本，并记录 `uia_control_missing`。把已验证可用的 QQ 版本写进 `docs/ARCHITECTURE.md`。

**验收**：
- [ ] 离线测试：替身窗口缺少任意一个控件时，批次进入等待状态，不发送。
- [ ] 工作台状态区显示 QQ 和 Edge 版本。
- [ ] 【需实机】在当前工作机上自检通过，版本号写进 PR。

### T08 用 Edge 策略放行 QQ 协议

**问题**：`lanhost/support.confirm_qq_dialog()` 通过 UI 自动化点击 Edge 的“打开 QQ”确认框，界面一变就会失效。

**做法**：在工作机安装脚本（`lanhost/install.ps1` 或 `install_helpers.ps1`）中，为本机 Edge 写入 `AutoLaunchProtocolsFromOrigins` 策略，只放行 QQ 唤起实际用到的协议，以及 T03 / 现有流程中实测到的来源域名。先通过实测确认协议名和来源域名，不要凭猜测填写。卸载或重置时移除该策略。保留 `confirm_qq_dialog` 作为后备。

**验收**：
- [ ] 安装脚本的测试（`tests/test_lan_install.py`）覆盖策略写入和移除。
- [ ] 只放行必要的协议和域名，不用通配符放行所有来源。
- [ ] 【需实机】策略生效后，首次唤起 QQ 不再出现确认框。在 `edge://policy` 页面确认，截图（不含聊天内容）附进 PR。

### T09 发送待核实项的自动复核

**问题**：发送结果待核实（`send_uncertain`）时，`runner.inquire()` 会把 `self._stop` 设为 True，整批停止，无人值守时会一直停着。

**做法**：出现待核实后，等待 3–5 秒，在同一会话中读取消息。如果在本次尝试时间之后找到我方发出的、内容完全一致的消息，就改为已发送，记录消息 ID，然后继续下一家。找不到，或会话已经变化，就保持待核实并按原逻辑停止。**任何情况下都不自动重发。**`dispatch.process_one` 的回复发送也按同样方式复核。

**验收**：
- [ ] 离线测试：找到消息时改为 `sent` 并继续；找不到时保持 `send_uncertain` 并停止；两种情况都不会再次调用 `send_text`。
- [ ] 每次复核都记录 `send_uncertain` incident，并注明复核结果。

### T10 记录被吞掉的异常

**做法**：把 `runner.py`、`qq.py`、`icnet.py` 中 `except Exception: pass` 或只 `return False` 的地方逐个检查。行为不变，但通过 `incidents.record(..., severity="debug")` 记下异常类型和位置（不记正文）。

**验收**：
- [ ] PR 中列出修改过的每一处。
- [ ] 不改变任何函数的返回值或控制流（现有测试全部通过）。

### T11 工作机环境检查

**做法**：在自检和工作机状态页加入以下检查：电源方案是否会睡眠、是否会自动锁屏、Windows 更新使用时段是否设置、QQ 是否开启了独立聊天窗口（如能检测）。只提示，不自动修改系统设置。`docs/dual-machine.md` 补充建议的设置步骤。

**验收**：
- [ ] 各项检查有离线测试（注册表和 powercfg 读取使用替身）。
- [ ] 状态页能显示每项检查的结果和修改建议。

**验收**：
- [ ] `ui_smoke.py` 或 `lan_ui_smoke.py` 覆盖：勾选 3 行并确认后产生 3 条 outbox，每条 `request_id` 不同。
- [ ] 重复点击不会重复入队（沿用 `request_id` 去重）。

## 五、大模型接入

### T16 回复意图分类与固定话术库

**做法**：
- `llm.parse_reply` 的输出增加 `intent` 字段，取值固定为：`ask_qty`、`ask_brand`、`ask_target_price`、`ask_tax`、`ask_company`、`ask_contact`、`quoted`、`no_stock`、`pending`、`other`。
- 新增话术库（`settings.toml` 的 `[replies]` 表，在设置页可编辑）：每个意图对应几条由我们自己写的固定回复，可以使用 `{part}`、`{qty}`、`{qtyk}` 等已知字段。
- 有对应话术的意图，建议回复优先使用话术，模型只负责选择和填入字段；没有对应话术时才由模型生成。界面上标出哪条来自话术库、哪条由模型生成。
- 话术中不得出现模型编造的价格、公司信息或承诺（沿用现有提示词规则）。

**验收**：
- [ ] 离线测试（模型用替身）：每种意图都能正确选中话术并填入字段。
- [ ] `intent` 值不在列表中时归为 `other`（`llm.normalize` 测试覆盖）。
- [ ] 设置页可以编辑和保存话术库。

### T17 建议采纳统计，用真实回复做示例

**做法**：用户发送回复时，记录它对应的建议（话术库、模型生成或手写），以及原样采用、修改后采用还是没用（`suggestion_edited` / `suggestion_rejected` incident）。从“修改后采用”和“手写”的真实回复中，按意图各挑最近 3–5 条作为示例加入生成提示词（只用我方自己发出的文字）。提示词中加入风格约束：短句、口语、不用感叹号、不写“感谢您的回复”之类的客套话。

**验收**：
- [ ] 采纳情况能按意图统计，并出现在 T20 报告中。
- [ ] 示例只取我方发出的消息，测试断言不包含供应商消息。

### T18 大模型决定下一步（白名单动作）

**做法**：
- 新增 `inquiry/agent.py`。每收到一轮回复后，模型从固定的动作列表中选择下一步：`reply_with_template`、`ask_lead_time`、`ask_batch`、`close_no_stock`、`wait`、`need_human`，并给出理由。
- 每个意图都有“自动发送”开关（`[autopilot]`），**全部默认关闭**。关闭时，模型的选择只作为建议显示在 T15 的列表中。
- 以下情况始终是 `need_human`，不能被设置覆盖：涉及价格还价、下单、付款、交换微信或电话、提供公司资质，以及模型输出无法解析。
- 自动发送仍走 `outbox`、身份复核和全局发送限速。

**验收**：
- [ ] 离线测试：所有“始终人工”的情形都返回 `need_human`，即使相关开关全部打开。
- [ ] 开关全部关闭时，不产生任何 outbox（测试覆盖）。
- [ ] 模型返回列表外的动作时，按 `need_human` 处理。
- [ ] `DECISIONS.md` 记录“脚本执行、模型判断、动作白名单”的取舍。

### T19 大模型备用切换

**做法**：`.env` 中可选配置第二套 `FALLBACK_API_KEY`、`FALLBACK_BASE_URL`、`FALLBACK_MODEL`（兼容 OpenAI 接口）。主模型超时或连续失败 2 次时，`analysis` 和 `agent` 自动改用备用模型，并记录 `llm_timeout` incident；主模型恢复后切回。没有配置备用时，行为与现在一致。

**验收**：
- [ ] 离线测试：主模型替身超时后改用备用模型，结果正常入库。
- [ ] 没有配置备用时，失败重试逻辑与现在一致（`analysis` 最多重试 3 次）。
- [ ] `.env.example` 和 README 补充说明，日志中不出现密钥。
